# M2.5 Client Mode Plan

**Status**: Plan only (not yet implemented)  
**Milestone**: M2.5  
**Goal**: tollgate-rs can pay upstream TollGate routers as a drop-in replacement for Go v1's `upstream_session_manager`

## 1. Current State

### What We Have (Rust)
The Rust codebase already has a working `V1Client<W: Wallet>` in `crates/tollgate-net/src/v1/mod.rs` that implements:

- **`connect()`**: Fetch ad → select pricing → create token → POST payment → parse session
- **`poll_usage()`**: GET `/usage` → parse `usage/allotment` → check renewal threshold
- **`renew()`**: Create new token → POST → update session allotment
- **`run()`**: Infinite loop — connect → poll → auto-renew
- **Session recovery**: Checks `/usage` first; if allotment > 0, re-attaches without payment

Supporting infrastructure:
- `TollGateHttpClient` (`http.rs`): HTTP client for `:2121` endpoints (GET /, POST /, GET /usage)
- `TollGateAdvertisement`, `SessionEvent`, `NoticeEvent` (`nostr_events.rs`): Nostr event parsing
- `select_cheapest_compatible()` (`pricing.rs`): Pricing selection with mint compatibility
- `probe_gateway()` / `probe_url()` (`upstream_detector.rs`): Upstream discovery
- `V1ClientConfig`: Full configuration struct

### What Go v1 Has That We Don't

| Go v1 Component | Lines | Purpose | Rust Equivalent |
|-----------------|-------|---------|-----------------|
| `upstream_session_manager.go` | 223 | Orchestrator: manages multiple upstream sessions by gateway IP | **Missing**: Multi-gateway session manager |
| `session.go` | 476 | Single session lifecycle: create, pay, renew, recover, stop | **Exists**: `V1Client` covers ~70% |
| `upstream_usage_tracker.go` | 304 | Polls `/usage` every 1s, triggers renewal callback | **Exists**: `V1Client::run()` but less granular |
| `tollgate_prober.go` | 274 | HTTP probe with retries, context cancellation, captive portal trigger | **Partial**: `probe_gateway()` exists but no retries |
| `pricing.go` | 159 | Budget validation, trust policy, allotment calculation | **Partial**: `pricing.rs` covers selection only |
| `token_recovery.go` | 71 | Auto-recover failed payment tokens + save to file | **Missing** |
| `wireless_gateway_manager/` | ~2144 | WiFi STA/AP management via UCI/ubus | **Out of scope** for M2.5 (M4) |
| `cli/server.go` | 854 | Unix socket CLI for wallet/upstream/status commands | **Missing** |

### Key Differences: Go v1 vs Rust V1Client

1. **Concurrency model**: Go uses goroutines + mutex per session. Rust `V1Client` is `&mut self` (single-task). Needs refactor to `Arc<Mutex<>>` or actor model for multi-gateway support.
2. **Usage polling granularity**: Go polls every 1s with tracker-level throttling (10s between payment triggers). Rust polls every `poll_interval_secs` (configurable).
3. **Renewal offset**: Go renews N units before exhaustion (`renewalOffset`). Rust uses a fraction threshold (`renewal_threshold: 0.0–1.0`). Semantically equivalent but configured differently.
4. **Token recovery**: Go auto-recovers failed tokens via `merchant.Fund()` and falls back to file persistence. Rust has no recovery mechanism.
5. **Payment throttling**: Go has two layers: tracker (10s) + session (5s). Rust has none explicitly.
6. **Captive portal trigger**: Go hits `:80` after probe as a workaround. Not needed for v2.
7. **Trust policy**: Go has allowlist/blocklist/default-policy for upstream pubkeys. Rust has none.

## 2. Implementation Plan

### Wave 1: Hardening V1Client (Foundation)

Fill in the gaps in the existing single-session client before building the multi-gateway manager.

#### W1-1: Token Recovery
- **File**: `crates/tollgate-net/src/v1/recovery.rs` (new)
- **What**: On payment failure, attempt `wallet.receive()` to reclaim the token. If that fails, log the token for manual recovery.
- **Tests**: Unit test recovery with MockWallet, test file-write fallback
- **Go reference**: `token_recovery.go`

#### W1-2: Probe Retries
- **File**: `crates/tollgate-net/src/v1/http.rs` (modify)
- **What**: Add retry logic to `TollGateHttpClient::fetch_advertisement()` with configurable retry count and delay. Context cancellation via `CancellationToken`.
- **Tests**: Unit test retry with mock HTTP server
- **Go reference**: `tollgate_prober.go` lines 73-138

#### W1-3: Payment Throttling
- **File**: `crates/tollgate-net/src/v1/mod.rs` (modify)
- **What**: Add `last_payment_attempt: Instant` to V1Client. In `renew()`, skip if < 5s since last attempt. Prevents renewal storms on network hiccups.
- **Tests**: Unit test throttle enforcement
- **Go reference**: `session.go` lines 222-233

#### W1-4: Budget Validation
- **File**: `crates/tollgate-net/src/v1/pricing.rs` (modify)
- **What**: Add `validate_budget()` (already exists but verify completeness), `validate_trust_policy()`, `calculate_steps_from_budget()`.
- **Tests**: Unit tests for each validation function
- **Go reference**: `pricing.go`

### Wave 2: Multi-Gateway Session Manager

Manage multiple concurrent upstream sessions (one per gateway).

#### W2-1: UpstreamSessionManager
- **File**: `crates/tollgate-net/src/v1/session_manager.rs` (new)
- **What**: 
  - `HashMap<String, UpstreamSession>` keyed by gateway IP
  - `handle_gateway_connected(ip, interface, mac)` — probe → create session → start tracker
  - `handle_disconnect(interface)` — stop all sessions on that interface
  - `get_active_sessions()` — return snapshot
  - `stop()` — shutdown all
- **Design choice**: Use `Arc<Mutex<HashMap<...>>>` or tokio MPSC actor. Given the Go v1 uses mutex-protected maps, `Arc<Mutex<>>` is the straightforward port.
- **Go reference**: `upstream_session_manager.go`

#### W2-2: Background Usage Tracker
- **File**: `crates/tollgate-net/src/v1/usage_tracker.rs` (new)
- **What**: Tokio task that polls `/usage` at configurable interval, calls renewal callback when threshold is reached.
  - Spawn one tracker per active session
  - Each tracker holds a `CancellationToken` for clean shutdown
  - Reports usage via channel or callback
- **Go reference**: `upstream_usage_tracker.go`

#### W2-3: Integration — Glue Session Manager + V1Client
- **File**: `crates/tollgate-net/src/v1/session_manager.rs` (extend)
- **What**: Session manager spawns `V1Client` instances (or wraps their HTTP calls) for each discovered gateway. Background tracker calls `renew()` via the client.
- **Key decision**: V1Client is currently `&mut self`. For concurrent use, either:
  - (A) Refactor to `Arc<Mutex<V1Client>>` — simplest
  - (B) Split into `V1ClientState` (shared) + methods that take `&self` — cleaner
  - **Recommendation**: (A) for parity, (B) can be a follow-up refactor

### Wave 3: CLI Server

Unix domain socket CLI for operator control. Matches Go v1's `cli/server.go`.

#### W3-1: CLI Protocol
- **File**: `crates/tollgate-net/src/v1/cli/mod.rs` (new)
- **What**: 
  - Listen on `/var/run/tollgate.sock`
  - JSON protocol: `{"command": "...", "args": [...], "flags": {...}}`
  - Response: `{"success": bool, "message": "...", "data": ...}`
- **Commands to implement**:
  - `wallet balance` — total balance across all mints
  - `wallet info` — per-mint balances
  - `wallet fund <token>` — receive Cashu token
  - `wallet drain cashu` — drain all mints to Cashu tokens
  - `upstream scan` — scan for available upstream networks
  - `upstream connect <ssid> [passphrase]` — connect to upstream
  - `upstream list-upstream` — list configured STA interfaces
  - `upstream remove-upstream <ssid>` — remove STA config
  - `status` — service status
  - `version` — version info
- **Go reference**: `cli/server.go`

#### W3-2: Streaming Connect
- **File**: `crates/tollgate-net/src/v1/cli/mod.rs` (extend)
- **What**: The `upstream connect` command sends progress updates as NDJSON (one JSON object per line) during the multi-step connect process.
- **Go reference**: `cli/server.go` lines 693-806

### Wave 4: Testing

## 4. Scope Boundaries

### In Scope for M2.5
- Everything in Waves 1-4 above
- Cashu token payments (bootstrap mode)
- LN invoice payments (using existing `/ln-invoice` endpoint)
- Multiple concurrent upstream sessions
- CLI control interface

### Explicitly Out of Scope
- **WiFi STA/AP management** (`wireless_gateway_manager/`) — This is M4 (tollgate-net IP peering). It requires OpenWrt-specific UCI/ubus calls and is OS-specific.
- **Spilman payment channels** — M3 scope
- **Real traffic gating** (iptables/nftables) — M4 scope  
- **Nostr relay integration** — explicitly excluded by user
- **FIPS mesh** — M6 scope

### Dependencies
- M2.5 depends on M2 (✅ complete) for Cashu wallet operations
- M2.5 client mode can be tested against the Rust server OR the Go v1 server
- M2.5 does NOT depend on M3 (Spilman channels)

## 7. Key Design Decisions to Make

### D1: Concurrency model for V1Client
**Options**:
- (A) `Arc<Mutex<V1Client<W>>>` — session manager wraps each client
- (B) Split V1Client into state + methods, use actor model with tokio channels
- (C) Keep V1Client as-is, spawn a task per gateway that owns the client exclusively

**Recommendation**: (C) — each upstream session gets its own `tokio::spawn` task that owns a `V1Client`. No shared mutable state needed. The session manager holds `JoinHandle`s and `CancellationToken`s. This is the most Rust-idiomatic approach.

### D2: CLI server architecture
**Options**:
- (A) Separate binary (`tollgate-cli`) that connects to the running `tollgate-net` via Unix socket
- (B) Built into `tollgate-net` binary, CLI socket is part of the server

**Recommendation**: (B) — matches Go v1. The CLI server is part of the main binary, listening on `/var/run/tollgate.sock`. A thin CLI client binary can be added later.

### D3: Configuration format
Go v1 uses a custom JSON config. Rust should use TOML (already in the codebase).
- `tollgate.toml` with `[client]` and `[server]` sections
- Client config includes: preferred allotment, renewal threshold, max prices, accepted mints, trust policy
